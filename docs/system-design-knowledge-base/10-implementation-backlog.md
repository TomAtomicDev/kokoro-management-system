# 10 — Implementation Backlog

Tasks are grouped by phase (Doc 09) and ordered by execution priority within each phase.
ID format `KOK-xxx`. Every task follows the Definition of Done (Doc 08 §5) and the playbook in
Doc 08 §3 when it adds/changes an event type.

**Size:** S ≤ half day · M ≤ 1.5 days · L ≤ 3 days (AI-assisted).

**🧠 Required intelligence (1–5)** — guides which AI model tier to assign the task to:


| 🧠  | Meaning                                                                                         | Typical model tier                                      |
| --- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| 1   | Mechanical: config, boilerplate, copy from a spec that leaves no decisions                      | small/fast model                                        |
| 2   | Routine: well-trodden patterns, spec is complete, low ambiguity                                 | small/mid model                                         |
| 3   | Standard engineering: integrate several documented pieces, some local judgment                  | mid model                                               |
| 4   | Complex logic: money math, state machines, concurrency/atomicity, subtle edge cases             | frontier model                                          |
| 5   | Design-heavy: reconciling multiple KB docs, API/prompt design, correctness is business-critical | frontier model + human review of the plan before coding |


Rule of thumb: anything touching **money arithmetic, the kardex, derived-row regeneration, or
prompts/evals** is 4–5 regardless of apparent size.

**Status** — tracks development progress per task:


| Status         | Meaning                                                        |
| -------------- | -------------------------------------------------------------- |
| 📋 To Do       | Not started                                                    |
| 🔨 In Progress | Actively being worked on                                       |
| 👀 In Review   | PR open / awaiting staging smoke-test                          |
| ✅ Done         | Merged and meets the Definition of Done (Doc 08 §5)            |
| 🚫 Blocked     | Blocked on a dependency, decision, or external action          |
| ⏭️ Deferred    | Deliberately deferred/descoped for now (record why in the row) |

## Phase 3.2 — User-Test 1 Review (GH #23)

Added 2026-08-11. The owner's first hands-on session on staging produced ~70 observations
(issue [#23](https://github.com/TomAtomicDev/kokoro-managemnt-system/issues/23)). The review
meeting closed every one of them; the decisions — agreed business rules, what was rejected and
why, and the risks accepted knowingly — are recorded in
[`docs/development/acuerdos-prueba-usuario-1.md`](../development/acuerdos-prueba-usuario-1.md).
**That document is the source for every task below; read the relevant section before starting a
task, and do not re-derive a rule from this table alone.**

The phase runs in four blocks, in this order (owner's decision):

- **Block A — Quick wins.** Cheap, low-risk, no migrations. Ships first so the owner can keep
  testing comfortably while the structural work is built. Highly parallelizable.
- **Block B — Presentation/Combo model.** The structural change: packaging stops being a sale
  line and becomes a component of a new **Envasado/Armado** (packing/assembly) event that
  produces stockable `FINISHED` presentations and combos. Touches the catalog, the kardex, WAC
  replay and sales. Must land **before real data exists** — retrofitting it afterwards means
  migrating catalog, stock and historical costs.
- **Block C — Sessions & orders.** Domain changes with migrations, same go-live reasoning.
- **Block D — Forms, validation & tools.** UI surface only; can land after go-live without
  migrating anything.

**Go-live gate:** the business goes live on real data at the end of Block C. Two hard
prerequisites: (1) **KOK-073** (`replacement_cost_history`, Phase 5.5) is pulled forward and
must be deployed **before the owner's first real purchase** — that series cannot be
reconstructed backwards; (2) staging data is wiped and re-seeded after Block B, since the
pre-assembly catalog shape is not migrated forward.

Cross-cutting for this phase: every schema change ships with its KB amendment in the same PR
(D-6); all new UI strings go to `i18n/es.ts` (D-9); anything touching WAC, the kardex or replay
carries property tests (Doc 11 §2).

**Task descriptions below were checked against the code on 2026-08-11** by four read-only
verification passes (sales/packaging, costing/replay, sessions, orders/counts/UI). Where a
description cites a file, a line count or a "verified" claim, it came from that pass — trust it
over the original review notes, which got several details wrong. The single most important finding:
**the replay dependency graph is trivially extensible but the cost cascade it feeds is not**, which
is why KOK-150 exists as a separate prerequisite refactor. Anyone scoping KOK-125 off
`dependency-graph.ts` will underestimate it by roughly five times.

**Area** is a code-location label, not a role: `web` = the change lives inside `apps/web`,
`backend` = `apps/worker`, `shared` = `packages/shared`, `full` = the whole vertical (schema →
service → route → UI), `docs` = KB only. Phases 0–3 spell the first one `ui`; same meaning.

**Design-first tasks.** Five items below introduce new visual patterns rather than filling in an
existing one, and need a design decision agreed against Doc 06 (§2–§4), Doc 07 and
`.design/foundations/` **before** implementation starts — treating them as pure coding is how they
come out wrong: **KOK-105** (PWA icon set, favicon, offline dialog), **KOK-134** (weekly calendar
layout), **KOK-140** (the full-page form pattern every later form inherits), **KOK-148**
(calculator keypad), **KOK-149** (header timer chip). The other UI tasks are implementation

## Phase 5.5 — Business Health Data

Added 2026-07-27. G2 and G3 are the two goals the owner feels daily, and until now they were
served by one table and a pair of StatCards. This phase turns the data already being recorded
into answers she can act on, under three rules:

1. **Bs, not percentages.** "Margen 8%" prompts nothing; "este mes esto te dejó Bs 40 en vez de
 Bs 340" prompts a price change. Every metric here resolves to money or to Bs/hour.
2. **No metric invents history.** Each row below names the stored series it reads. Where a
 series does not exist we either start recording it (KOK-073) or use an honest substitute and
 say so — never an approximation presented as a record. This is the KOK-036 lesson.
3. **Placement follows attention.** The dashboard gets the number, SC-13's "Salud del negocio"
 tab gets the chart, the Monday Telegram digest gets the one sentence that would otherwise go
 unread (the owner is a solo operator; a dashboard she does not open explains nothing).

All of this is price-vs-cost arithmetic: per-unit rates are integer milli-centavos per whole unit
(`_mc`) and `qty` is milli-units (ADR-017, Doc 04 §2), so convert through `shared/money.ts`'s
helpers before a figure reaches an axis label. Read the `dataviz` skill and Doc 06 §3's shared
chart theme before the first chart.
